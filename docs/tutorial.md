# Adaptive Ads — Technical Walkthrough

This document explains how Adaptive Ads works from the moment a telemetry file arrives to the point where an analyst can query an analytics mart.

It is intentionally more detailed than the root README.

Use this document when you want to understand the implementation, set the project up again after a long break, or trace a piece of data through the system.

---

# 1. What Are We Building?

Adaptive Ads processes telemetry generated by a video-streaming and advertising platform.

The system receives four types of events:

```text
watch_events
ad_events
page_view_events
auth_events
```

The goal is to turn these raw events into reliable analytical datasets.

At a high level:

```text
Raw Events
    ↓
GCS / Parquet
    ↓
Airflow
    ↓
BigQuery Staging
    ↓
dbt Transformations
    ↓
Dimensions + Facts
    ↓
Analytics Marts
    ↓
Looker Studio
```

---

# 2. Why This Architecture?

Each tool has a specific responsibility.

| Component      | Responsibility                            |
| -------------- | ----------------------------------------- |
| GCS            | Store raw telemetry files                 |
| Airflow        | Decide when and how pipelines run         |
| BigQuery       | Store and query warehouse data            |
| dbt            | Transform raw data into analytical models |
| GitHub Actions | Validate changes automatically            |
| Looker Studio  | Consume the final analytical datasets     |

The separation is intentional.

Airflow handles **orchestration**.

dbt handles **transformation**.

BigQuery handles **storage and analytical execution**.

---

# 3. Raw Data

Raw telemetry arrives as Parquet files.

Example:

```text
watch_events/
    2026-08-01/
        events.parquet

ad_events/
    2026-08-01/
        events.parquet

page_view_events/
    2026-08-01/
        events.parquet

auth_events/
    2026-08-01/
        events.parquet
```

Parquet was chosen because telemetry data is naturally tabular and columnar storage is useful for analytical workloads.

The raw layer should remain as close as possible to the source data.

---

# 4. Airflow Orchestration

The main DAG is responsible for coordinating ingestion and transformations.

Conceptually:

```text
                 adaptive_ads_dag
                        |
       +----------------+----------------+
       |                |                |
 watch_events       ad_events      page_views
       |                |                |
       +----------------+----------------+
                        |
                    dbt run
                        |
                    dbt test
```

The ingestion tasks are implemented using reusable `TaskGroup`s.

Instead of writing:

```text
watch ingestion code
ad ingestion code
page ingestion code
auth ingestion code
```

the pipeline uses a shared implementation driven by configuration.

---

# 5. EVENT_CONFIG

The event configuration acts as the registry for supported event streams.

Conceptually:

```python
EVENT_CONFIG = {
    "watch_events": {...},
    "ad_events": {...},
    "page_view_events": {...},
    "auth_events": {...},
}
```

The configuration contains the information needed to build the corresponding ingestion tasks.

This gives us a useful property:

> Adding a new event type should require configuration changes rather than another copy of the ingestion implementation.

---

# 6. Idempotent Ingestion

One of the most important operational problems is retry safety.

Imagine an Airflow task loads:

```text
2026-08-10
```

and then fails after partially completing.

If the task simply runs another `INSERT`, we could end up with:

```text
Original rows
+
Retry rows
=
Duplicates
```

Instead, the pipeline uses a partition-scoped:

```text
DELETE
   ↓
INSERT
```

strategy.

For a given execution window:

```text
Delete existing partition
        ↓
Load partition again
```

Running the same operation twice produces the same final state.

That is the core idea behind idempotency.

# 7. Staging Layer

Raw events first enter the staging layer.

Examples:

```text
stg_watch_events
stg_ad_events
stg_page_views
stg_auth_events
```

The staging layer is responsible for cleaning and standardizing source data.

Typical operations include:

* Naming normalization
* Type conversion
* Timestamp normalization
* Null handling
* Source-specific cleanup

Staging models are generally views because they do not need to maintain a second physical copy of the raw data.

---

# 8. Dimensional Model

After staging, the data is transformed into a Kimball-style dimensional model.

The warehouse contains:

```text
                 dim_users
                     |
                     |
dim_movies ---- fact_streams ---- dim_location
                     |
                     |
              analytical marts
```

The main components are:

### Dimensions

```text
dim_users
dim_movies
dim_location
```

### Facts

```text
fact_streams
fact_ad_events
```

The important concept is **grain**.

For example:

```text
fact_streams
= one row per streaming event
```

and:

```text
dim_users
= one row per user per subscription-tier validity period
```

Defining grain explicitly prevents many downstream analytical problems.

---

# 9. SCD Type 2

Users can change subscription tiers.

For example:

```text
User 101
Free
   ↓
Paid
```

We don't want to overwrite the original state.

Instead:

```text
user_id | tier | valid_from | valid_to | is_current
----------------------------------------------------
101     | Free | Jan 01     | Mar 14   | false
101     | Paid | Mar 14     | NULL     | true
```

This allows historical analysis.

If a stream happened on February 20, the warehouse can determine that the user was a Free subscriber at that point in time.

The implementation uses SQL window functions such as:

```sql
LAG()
SUM()
LEAD()
```

to identify state changes and construct validity periods.

---

# 10. Incremental Facts

The streaming and advertising fact tables can become very large.

Rebuilding the entire table every hour would be unnecessary.

Instead:

```text
New data
+
recently changed data
        ↓
Incremental MERGE
```

The important models are:

```text
fact_streams
fact_ad_events
```

These tables are:

* Incrementally materialized
* Partitioned by day
* Clustered on commonly filtered columns

---

# 11. Late-Arriving Data

Events do not always arrive in perfect chronological order.

Suppose the pipeline processes:

```text
September 7
```

but an event generated on:

```text
September 5
```

arrives late.

If we only process September 7, that event will never enter the warehouse.

The solution is a sliding lookback:

```text
Current day
     ↓
Current day - 3 days
```

Every incremental run therefore checks the most recent three days.

This provides a practical balance between:

* Data completeness
* Query cost
* Processing time

---

# 12. BigQuery Optimization

The warehouse uses two important BigQuery optimization techniques.

## Partitioning

Large fact tables are partitioned by day.

```text
2026-09-01
2026-09-02
2026-09-03
...
```

A query targeting one day doesn't need to scan the entire table.

## Clustering

Frequently filtered columns are used for clustering.

Examples include:

```text
campaignId
adPlacement
userId
movieId
```

Together, partitioning and clustering reduce unnecessary data scanning.

---

# 13. Incremental Predicates

A particularly important optimization is restricting the target side of incremental merges.

Without a predicate, BigQuery may scan a much larger portion of the target table.

The pipeline instead limits the merge to the relevant recent partitions.

Conceptually:

```text
Entire fact table
       ↓
Recent 3-day partitions
       ↓
MERGE
```

This is one of the main cost-control mechanisms in the project.

# 14. Analytical Marts

The core warehouse is not necessarily the final dataset consumed by analysts.

The marts layer provides business-friendly models.

### `daily_ad_metrics`

Contains metrics such as:

```text
eCPM
CTR
ad impressions
clicks
revenue / yield
```

### `user_engagement_summary`

Contains:

```text
watch hours
watch duration
subscription tier
daily engagement
```

### `campaign_performance_cube`

Provides campaign-level analytical dimensions such as:

```text
campaign
placement
tier
date
```

These models are designed to be consumed by BI tools.

# 15. Data Contracts

A data pipeline should not silently accept arbitrary schema changes.

The repository therefore defines declarative contracts under:

```text
contracts/
```

A contract describes expectations around fields and their structure.

The validation script:

```text
scripts/validate_contracts.py
```

checks that the repository remains consistent with those expectations.

This helps catch schema drift before it becomes a downstream analytics problem.

---

# 16. Testing Strategy

Testing is intentionally split into multiple layers.

```text
                 Full Repository
                       |
                +------+------+
                |             |
             dbt tests     Python tests
                |             |
          SQL assertions   Unit tests
                |
         Data contracts
```

The local validation suite performs nine categories of checks:

1. Python compilation
2. Unit tests
3. Airflow DAG validation
4. SQL integrity checks
5. dbt schema validation
6. Security scanning
7. Performance safeguards
8. Operational tooling checks
9. Documentation validation

Run everything with:

```bash
./scripts/validate.sh
```

# 17. Operational Tools

The `scripts/` directory contains tools for maintaining the platform.

### Backfills

```bash
python scripts/backfill.py --dry-run
```

The backfill utility validates the requested time range and shows what would be processed before making changes.

### Schema checks

```bash
python scripts/check_schema.py
```

This detects changes such as:

```text
Added column
Removed column
Type change
```

These tools are useful when operating the pipeline rather than just developing it.

# 21. Disaster Recovery

The project documents recovery procedures for common pipeline failures.

The target objectives are:

```text
RPO ≤ 1 hour
RTO ≤ 30 minutes
```

BigQuery Time Travel is used as one of the recovery mechanisms for recently modified or deleted data.

The recovery documentation covers scenarios such as:

* Failed ingestion
* Corrupt partitions
* Schema changes
* Failed transformations
* Duplicate data
* Broken deployments
* Warehouse recovery

# 22. How to Trace One Event

When debugging the system, start with a single event.

For example:

```text
watch event
    ↓
Parquet file
    ↓
GCS
    ↓
Airflow ingestion
    ↓
stg_watch_events
    ↓
fact_streams
    ↓
user_engagement_summary
    ↓
Looker dashboard
```

This is one of the easiest ways to understand the entire architecture.

If you forget how the system works months later, follow one event through the pipeline instead of trying to understand the entire repository at once.

If you forget everything else, remember this:

```text
              RAW
               │
               ▼
        ┌──────────────┐
        │    GCS       │
        │   Parquet    │
        └──────┬───────┘
               │
               ▼
        ┌──────────────┐
        │   Airflow    │
        │ Orchestration│
        └──────┬───────┘
               │
               ▼
        ┌──────────────┐
        │   BigQuery   │
        │   Staging    │
        └──────┬───────┘
               │
               ▼
        ┌──────────────┐
        │     dbt      │
        │ Transform    │
        └──────┬───────┘
               │
        ┌──────┴───────┐
        ▼              ▼
   Dimensions        Facts
        │              │
        └──────┬───────┘
               ▼

        │    Marts     │
```

**BigQuery stores and computes.**

**dbt transforms and tests.**

**Dimensions describe entities.**

**Facts record events.**

**Marts answer business questions.**

**CI and contracts protect the pipeline.**

**Operational tooling makes it maintainable.**
